About Adobe Experience Cloud Cookies

Adobe Experience Cloud is a suite of enterprise marketing, analytics, and personalisation products. Three products within the suite set browser cookies on a website:

Adobe Experience Cloud ID Service (ECID) is the foundation layer. It assigns a unique Marketing Cloud ID (MCID) that persists across all Adobe products on the same domain. When any Adobe-instrumented page loads, ECID creates a visitor identifier and shares it with Analytics, Target, and Audience Manager so they can all recognise the same visitor. Without ECID, each Adobe product would track visitors independently with no cross-product linkage. ECID sets the AMCV_ and AMCVS_ cookies.

Adobe Analytics is Adobe's web analytics platform — comparable to Google Analytics 4. It tracks page views, user journeys, campaign performance, conversion funnels, and engagement metrics using server-side data collection (the /b/ss endpoint) and client-side cookies for session and visitor identification. Analytics uses AppMeasurement.js for data collection and sets several s_-prefixed cookies.

Adobe Target is Adobe's A/B testing and personalisation engine. It allows site owners to test multiple content variants and deliver personalised experiences based on visitor segments. Target uses cookies to maintain the visitor's session, track which test variants they've been assigned, and persist personalisation context across page loads. It loads via at.js.

Adobe Opt-In Service is Adobe's centralised consent API — unlike Google, Meta, and Bing which each have separate consent APIs, all Adobe products are controlled through a single adobe.optIn interface. A unique architectural advantage: when consent is initially denied, Adobe queues all tracking calls in memory. When consent is later granted, all queued page views and events replay automatically — zero data loss, unlike Google/Meta/Bing which permanently lose pre-consent activity.

Four ways Adobe cookies get set on a website

  1. ECID VisitorAPI.js — first-party (foundation for all Adobe products): Call Visitor.getInstance("ORG_ID@AdobeOrg"). Writes AMCV_ (24-month visitor ID) and AMCVS_ (session flag). Must load before Analytics and Target so they can read the shared visitor ID.
  2. Adobe Analytics AppMeasurement.js — first-party: Loads with a Report Suite ID. Sets s_cc, s_dur on every page. Sets s_vi (legacy visitor ID) and s_fid (fallback ID) when first-party visitor tracking is active. s_sq and s_ppv appear when Activity Map / scroll tracking is enabled.
  3. Adobe Target at.js — first-party: Loads with a Client Code. Sets mbox (session + PC/profile cache identifier, used to persist A/B test variant assignments) and at_check (library availability check). No third-party cookies.
  4. Adobe Launch / Experience Platform Tags (tag manager route): Adobe's own tag manager loads a single container script (assets.adobedtm.com). The container then fires ECID, Analytics, and Target tags based on configured rules — similar to how GTM fires Google tags.

Debug Helpers

  • Check ECID state (real ECID only): run Visitor.getInstance("YOUR_ORG_ID@AdobeOrg").getMarketingCloudVisitorID() in the browser console — returns the MCID stored in the AMCV_ cookie.
  • Check Opt-In consent state (real ECID only): run adobe.optIn.fetchPermissions(function(p){console.log(p)}, true) — returns the current consent state for all Adobe categories.
  • Check Target mbox state (real at.js only): run window.adobe.target.getOffer({...}) or inspect window.mboxFactories in the console.
  • Adobe Experience Cloud Debugger: install the Adobe Experience Platform Debugger Chrome extension to validate ECID, Analytics, and Target tag firing on the real implementation.
  • View this page's dummy cookies: open Cookie Reader — all Adobe cookies appear with correct category labels. Use the Analytics and Functional filters.

Adobe Opt-In Service — Enforcement Reference

Adobe has a single centralised consent API called the Opt-In Service (adobe.optIn), bundled with the ECID library. Unlike Google, Meta, and Bing which each have independent consent APIs, all Adobe products are controlled through this one interface. This is configured via the Visitor.getInstance() call with doesOptInApply: true.

Key architectural advantage — data queuing: When consent is initially denied, Adobe queues all Analytics page views and Target calls in memory. When consent is later granted, all queued calls replay — unlike Google, Meta, and Bing which permanently lose pre-consent page views.

Call Controls Effect Cookies Gated
preOptInApprovals: { aa: false, ecid: false } Analytics + ECID — default denied No AMCV_ cookie written; Analytics beacons queued, not sent AMCV_*, AMCVS_*, s_cc, s_dur, s_vi, s_fid
adobe.optIn.approve([ANALYTICS, ECID], true) Analytics + ECID — grant ECID writes AMCV_; Analytics activates and replays all queued page views All above unlocked + queued data replayed
preOptInApprovals: { target: false } Target — default denied No mbox cookie; Target personalisation calls queued mbox, at_check
adobe.optIn.approve([TARGET], true) Target — grant Target activates; test variants assigned; mbox written mbox unlocked
adobe.optIn.deny([ANALYTICS, ECID], true) Analytics + ECID — revoke Future cookies blocked; existing cookies must be deleted separately (Klaro handles this via cookie pattern /^AMCV_/, /^s_/) Blocked going forward

Category mapping for enforcement: Analytics toggle → controls aa (Adobe Analytics) + ecid (ECID — required for Analytics to function) together. Functional toggle → controls target (Adobe Target — A/B testing, classified as Functional not Marketing). The aam (Audience Manager) category is not mapped until AAM cookies are confirmed on customer sites.
